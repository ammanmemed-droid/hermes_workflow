# 项目审计与优化

仅在 L2/L3 的全项目审计、系统优化、性能改进或扫除 Bug 任务中读取。L1 不读取本文件。

## 先审计，后修改

先保持只读，建立现有测试和运行基线。每个问题必须包含：代码位置、触发条件、实际影响、根因、建议修复、回归风险和验证方式。不要根据 TODO、注释、命名或推测直接认定 Bug。

## 分批实施

按安全、日志、性能、服务发现或工程治理等主题拆分批次。每批明确目标、非目标、兼容约束和验收标准；先提交审计与方案，用户确认后只实施当前批次。完成并报告后停止，不自动进入下一批。

## 行为真实性

模拟、Mock、占位、降级、未执行或未连接真实依赖的结果必须明确标记为 `simulated`、`dry_run`、`degraded`、`unsupported`、`not_implemented` 或 `integration_unverified`。只有获得对应等级的真实证据时才能声明执行成功、集成通过或可发布。

## 优化证据

性能、并发、日志和资源优化必须先定义工作负载、环境、数据量、重复次数、主指标和护栏指标。修改前后使用相同条件实测对比；不得凭感觉宣布优化成功，也不得仅通过放大线程池、连接池或超时掩盖瓶颈。
